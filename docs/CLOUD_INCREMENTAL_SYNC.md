# همگام‌سازی افزایشی فضای کار

همگام‌سازی نخست یک بکاپ SQLite کامل را به‌عنوان پایه وارد می‌کند. پس از آن، triggerهای SQLite تغییرهای مشتری، فروشگاه، فاکتور، ردیف‌های فاکتور و قالب چاپ را ثبت می‌کنند و کلاینت فقط اسناد تغییرکرده را ارسال می‌کند؛ دریافت از وب نیز با cursor افزایشی انجام می‌شود. migration شمارهٔ ۱۴ قالب‌های چاپ ذخیره‌شدهٔ نسخه‌های قبلی را هم برای ارسال اولیه صف می‌کند.

## دریافت تغییرات

- سرور در `document_changes` برای اسناد موجود هنگام ارتقا backfill انجام می‌دهد و هر ایجاد، ویرایش، واردسازی یا tombstone جدید را با شناسهٔ افزایشی ثبت می‌کند.
- API `GET /api/v1/cloud/document-changes?after={cursor}&limit=200` تغییرها را صفحه‌بندی و برای هر سند به آخرین وضعیت ثبت‌شده در صفحه ادغام می‌کند.
- tombstone به کلاینت می‌رسد. دسکتاپ سند محلی متناظر را حذف می‌کند؛ اگر سوابق مالی یا وابستگی دیگری حذف را منع کند، تراکنش شکست می‌خورد و cursor جلو نمی‌رود تا تعارض رفع شود.
- cursor دریافت‌شده در جدول خصوصی `cloud_sync_state` در SQLite ذخیره می‌شود. کلاینت فقط پس از اعمال موفق همهٔ صفحه‌ها cursor را جلو می‌برد. قطع برنامه پیش از ذخیره ممکن است همان صفحه را تکرار کند؛ اعمال سندها idempotent است.
- تغییرهای محلی در `local_cloud_changes` ثبت می‌شوند. شناسهٔ ابری پایدار، نسخهٔ remote و آخرین snapshot مشترک در `cloud_document_map` نگهداری می‌شود؛ migration 17 ستون `base_data` را افزوده است. triggerها هنگام اعمال تغییرهای وب غیرفعال‌اند تا loop ایجاد نشود. قالب‌ها با همان فید ارسال/دریافت می‌شوند؛ کلیدهای اختصاصی وب در API هنگام push دسکتاپ حفظ می‌شوند.
- هنگام sync پایه، شناسهٔ کاربر API برای ساخت همان شناسه‌های deterministic که importer سرور از backup می‌سازد استفاده می‌شود؛ این کار از تطبیق حدسی ردیف‌ها در دستگاه اولیه جلوگیری می‌کند. مرز backup از رویدادهای ساخت نگاشت/قالب جدا نگه داشته می‌شود؛ تغییر محلی هنگام upload باعث توقف اعمال snapshot ابری می‌شود و رویدادهای قالب seed‌شده برای push افزایشی بعدی باقی می‌مانند.
- اگر نسخهٔ remote از نسخهٔ ذخیره‌شده جلوتر باشد، UI سیاست را توضیح می‌دهد و تأیید می‌گیرد؛ سپس کلاینت بر پایهٔ `base_data` تغییرهای مستقل فیلدها را سه‌طرفه ادغام و یک بار با نسخهٔ تازه تلاش می‌کند. تعارض یک فیلد یا آرایه طبق سیاست پذیرفته‌شدهٔ desktop-wins حل و تعداد آن در نتیجهٔ sync گزارش می‌شود. برای نصب‌های قدیمی که هنوز snapshot پایه ندارند، fallback صریح همان desktop-wins است تا پس از sync یک snapshot معتبر ذخیره شود.
- شناسهٔ cursor به کاربر محدود است و هیچ سندی از کاربر دیگر وارد پاسخ نمی‌شود.

## محدودیت‌های باقیمانده

پرداخت‌ها از مسیر idempotent موجود همگام می‌شوند. همگام‌سازی خودکار اختیاری دسکتاپ هر ۵ دقیقه اجرا می‌شود؛ فعال‌سازی آن رضایت صریح کاربر را برای ادغام فیلدی و انتخاب مقدار دسکتاپ در تعارض هم‌فیلدی ثبت می‌کند و چرخه‌ها هنگام اجرای عملیات دیگر نادیده گرفته می‌شوند. قالب چاپ در change feed دوطرفه است و تنظیمات صفحه، فونت، رنگ، نمایش مالیات/بانک، پیشوند شماره‌گذاری، متن پایانی و تصویرهای PNG/JPEG لوگو/مهر/امضا را منتقل و در PDF/HTML دسکتاپ اعمال می‌کند. هر تصویر حداکثر ۵۰۰ کیلوبایت و ۳۰۰۰×۳۰۰۰ پیکسل است. آزمون عملی در سرور تولید و رفتار هم‌زمان چند worker باقی است. بکاپ کامل جداگانه همچنان از دکمهٔ بکاپ در دسترس است.

## بررسی محلی

`dev.ps1 -NoRun` در Windows با Qt 6.12.0، آزمون‌های Go، vet، build برنامه و deploy کتابخانه‌های Qt را اجرا می‌کند. آزمون Go ارسال HTTP محلی، create/update/delete، tombstone، export اقلام و هزینهٔ فاکتور، seed شناسهٔ bootstrap، ادغام فیلدی مستقل و تعارض هم‌فیلدی، حفظ snapshot مشترک، ارتقای schema نسخهٔ ۱۶ به ۱۷، retry تعارض، cursor persistence و جلوگیری از بازتاب دادهٔ وب را پوشش می‌دهد. آزمون end-to-end PHP/MySQL برای API تا اجرای CI یا محیط نصب‌شده روی سرور تأییدشده محسوب نمی‌شود.

در ۲۰ نوامبر ۲۰۲۶، `go test -race ./internal/...` نیز برای تمام بسته‌های داخلی موفق شد. این نتیجه فقط از race detector در آزمون‌های داخلی خبر می‌دهد و جایگزین تست فشار یا آزمون هم‌زمانی چند worker روی MySQL/Redis تولید نیست.
