# معماری پیشنهادی

## اصول
- وابستگی‌ها به سمت Domain و Application باشند.
- UI، پایگاه داده، سیستم‌عامل و موتورهای خروجی جزئیات قابل تعویض باشند.
- محاسبات مالی تنها یک پیاده‌سازی مرجع داشته باشند.
- داده‌های ذخیره‌شده و Snapshot اسناد از تنظیمات جاری مستقل بمانند.
- معماری بر اساس نیاز واقعی کوچک و قابل تست نگه داشته شود؛ Interface صرفاً در مرزهای لازم ایجاد شود.

## لایه‌ها
1. **Domain:** موجودیت‌ها و قواعد پایدار؛ Invoice، InvoiceItem، Customer، IssuerProfile، Payment، Allocation، Numbering و قواعد مالی.
2. **Application:** موارد کاربرد مانند CreateInvoice، IssueInvoice، RecordPayment، SettleInvoice، SearchInvoices، Backup و Restore؛ کنترل تراکنش و هماهنگی عملیات.
3. **Ports/Contracts:** قراردادهای مورد نیاز برای ذخیره‌سازی، زمان، شماره‌گذاری و رندر، فقط در نقاطی که جداسازی واقعی لازم است.
4. **Adapters:** پیاده‌سازی SQLite، فایل‌سیستم، تقویم شمسی، PDF، XLSX و خدمات لایسنس.
5. **Presentation:** رابط Qt و ViewModel/Controller مناسب Binding انتخاب‌شده؛ دریافت ورودی، نمایش وضعیت و پیام خطا، بدون محاسبات مالی.

## جریان نمونه ایجاد فاکتور
UI → Application Use Case → اعتبارسنجی Domain → تراکنش SQLite (شماره یکتا + سند + اقلام + Snapshot) → نتیجه ساخت‌یافته → UI/Preview.
تولید PDF و XLSX باید مدل داده/نتیجه محاسبه مشترک را مصرف کند و محاسبات مستقل نداشته باشد.

## مرزبندی پیشنهادی کد
نام پوشه‌ها قطعی نیست و پس از بررسی Binding Qt و ساختار واقعی مخزن تثبیت می‌شود:
- internal/domain/
- internal/application/
- internal/ports/ (فقط در صورت نیاز)
- internal/adapters/sqlite/
- internal/adapters/pdf/
- internal/adapters/xlsx/
- internal/adapters/calendar/
- internal/presentation/qt/
- cmd/
- migrations/ یا مسیر نسخه‌بندی‌شده در ماژول storage
- docs/

## مدل داده اولیه
- Customer: شناسه پایدار و اطلاعات تماس
- IssuerProfile: پروفایل‌های صادرکننده
- Invoice: نوع سند، وضعیت، شماره، تاریخ، واحد پول، Snapshot طرفین و مجموع‌های محاسبه‌شده
- InvoiceItem: شرح، مقدار، واحد، قیمت صحیح، تخفیف و ترتیب نمایش
- Payment: شناسه یکتا، مبلغ صحیح، تاریخ، روش و مرجع اختیاری
- PaymentAllocation: تخصیص مبلغ پرداخت به یک سند؛ محدودیت یکتایی و کنترل مجموع تخصیص
- InvoiceSequence: سری شماره‌گذاری و مقدار بعدی، به‌روزرسانی تراکنشی
- Template/BankAccount/Settings: تنظیمات نمایشی و حساب‌ها
- AuditEvent: رویدادهای تغییر حساس با حداقل اطلاعات ضروری

این فهرست طرح مفهومی است، نه schema نهایی. نوع داده، قیدها و روابط در فاز SQLite مشخص می‌شوند.

## تراکنش و هم‌زمانی
شماره سند، درج سند و اقلام باید در یک تراکنش انجام شود. تخصیص پرداخت و مانده نیز باید اتمیک باشد. Foreign Key در هر اتصال فعال شود. قفل‌گذاری/Busy timeout و سیاست WAL پس از بررسی driver و الگوی دسترسی تعیین شوند.

## داده و امنیت
- مسیر داده در پوشه کاربر و خارج از نصب
- Migrationهای نسخه‌بندی‌شده و قابل تشخیص
- Backup سازگار با SQLite و اعتبارسنجی Restore
- Prepared Statements یا API امن driver
- عدم ثبت اطلاعات بانکی/شخصی در Log
- عدم ذخیره کلید خصوصی امضای لایسنس در کلاینت
- دسترسی به داده حتی پس از پایان لایسنس حفظ شود.

## نکات باز
- Binding Qt و مدل توزیع برنامه
- انتخاب driver SQLite و اثر مجوز/CGO
- کتابخانه PDF با پشتیبانی واقعی RTL و تعبیه فونت
- کتابخانه XLSX و مجوز آن
- قراردادهای محاسبه مالی، گردکردن و مالیات
- جزئیات Migration، Backup و ارتقای نصب

هر مورد باید با نمونه، تست و تصمیم ثبت‌شده بسته شود.
