# معماری لایسنس و قابلیت‌های پیشرفته

## وضعیت فعلی
دسکتاپ کد خریداری‌شده را از API وب فعال می‌کند، کلیدهای عمومی را دریافت و در فضای دادهٔ خصوصی ذخیره می‌کند، و claims را آفلاین بررسی می‌کند. صدور لایسنس در پنل وب فعلاً دستی است؛ فروش/تمدید آنلاین، چرخهٔ لغو روی سرور واقعی، و تأیید build نهایی با کلید تولید هنوز نیازمند آماده‌سازی انتشار هستند.

## طرح امضا
- قالب توکن: `base64url(JSON claims).base64url(Ed25519 signature)`؛ claims جدید شامل `key_id` است.
- `key_id` برابر ۱۶ رقم هگز اول SHA-256 کلید عمومی Ed25519 است و داخل payload امضاشده قرار می‌گیرد.
- امضا روی بایت‌های دقیق JSON انجام می‌شود؛ verifier قبل از بررسی امضا JSON را بازنویسی نمی‌کند.
- `GET /api/v1/licenses/public-key` و پاسخ فعال‌سازی، کلید فعال و حلقهٔ کلیدهای عمومی را می‌دهند؛ دسکتاپ حلقهٔ هم‌پاسخ فعال‌سازی را ترجیح می‌دهد تا چرخش هم‌زمان موجب mismatch نشود. دسکتاپ فقط کلید عمومی را نگه می‌دارد و claims قدیمی بدون `key_id` را نیز با حلقه بررسی می‌کند.
- کلید خصوصی فقط در محیط آفلاین/محدود صدور لایسنس نگهداری می‌شود و نباید در مخزن، برنامه، installer، log یا فایل‌های قابل دانلود عمومی قرار گیرد.
- تابع امضای تولیدی در بسته برنامه وجود ندارد؛ helper امضا فقط در تست‌ها قرار دارد.

## Claims
- `license_id`: شناسه یکتای لایسنس
- `product`: شناسه محصول ثابت `hesora`
- `subject`: شناسه یا نام مشتری غیرحساس
- `issued_at`, `not_before`, `expires_at`: زمان‌های Unix
- `installation_id`: اختیاری؛ شناسه تصادفی نصب محلی
- `features`: فهرست شناسه قابلیت‌ها

لایسنس بدون `expires_at` تاریخ انقضا ندارد. سیاست فروش باید مشخص کند که آیا این نوع مجوز مجاز است یا خیر.

## قابلیت‌ها
شناسه‌های اولیه در `internal/licensing/features.go` تعریف شده‌اند:
- رایگان: `basic.invoice`, `basic.customers`
- پیشرفته: `export.pdf`, `export.excel`, `templates.custom`, `payments.advanced`, `backup.advanced`

این کاتالوگ اولیه است؛ شناسه‌ها باید پیش از انتشار پایدار و در همه لایه‌های Application بررسی شوند. مخفی‌کردن دکمه در UI به‌تنهایی کنترل دسترسی محسوب نمی‌شود.

## فعال‌سازی و ذخیره‌سازی محلی
`licensing.FileStore` توکن، شناسهٔ نصب و حلقهٔ کلید عمومی را در دایرکتوری داده ذخیره می‌کند. فرمت قدیمیِ تک‌کلید در خواندن پذیرفته می‌شود. نوشتن با فایل موقت و rename انجام می‌شود و مجوز فایل محدود است.

1. مدیر سایت کد لایسنس را دستی از پنل صادر می‌کند.
2. کاربر کد را در برنامه وارد می‌کند؛ برنامه حلقهٔ کلید را از HTTPS می‌گیرد و endpoint فعال‌سازی کد را به همین نصب متصل می‌کند.
3. برنامه امضا، محصول، زمان، `key_id` و شناسهٔ نصب را بررسی می‌کند و سپس توکن و حلقه را ذخیره می‌کند.
4. قابلیت‌ها از طریق `RequireFeature` در Application بررسی می‌شوند.

برای چرخش کلید سرور، اپراتور `sudo bash bin/hesora.sh rotate-keys` را اجرا می‌کند. کلید عمومی قبلی در حلقه می‌ماند تا توکن‌های صادرشده معتبر بمانند؛ کلید خصوصی قبلی از config فعال کنار گذاشته می‌شود. کلیدهای عمومی دریافتی با کلید build-time ادغام می‌شوند تا نسخه‌های دسکتاپ به‌روزشده بتوانند توکن‌های قدیمی و جدید را بررسی کنند.

## رفتار انقضا و حفظ داده
- در حالت رایگان، قابلیت‌های پایه همچنان در دسترس هستند.
- در صورت انقضای لایسنس، قابلیت‌های پولی از نتیجه verifier اعطا نمی‌شوند.
- خطای لایسنس نباید خواندن، خروجی‌گرفتن از داده‌های پایه یا Backup ضروری کاربر را مسدود کند؛ سیاست دقیق قابلیت‌های پولی باید این اصل را رعایت کند.
- حذف یا خرابی فایل لایسنس نباید فایل SQLite یا داده‌های مشتری را حذف کند.

## محدودیت‌های امنیتی
- لایسنس آفلاین قابل کپی است؛ شناسه نصب مانع قطعی کپی یا دستکاری برنامه نیست.
- ساعت سیستم ممکن است عقب برده شود. verifier از زمان جاری سیستم استفاده می‌کند؛ جلوگیری قابل اتکا از rollback در برنامه دسکتاپ آفلاین تضمین‌پذیر نیست.
- مهاجم دارای کنترل کامل روی دستگاه می‌تواند کد برنامه را Patch کند یا بررسی entitlement را دور بزند. این راهکار بازدارندگی پایه است، نه DRM غیرقابل شکست.
- شناسه نصب تصادفی از جمع‌آوری شماره سریال سخت‌افزار/شناسه‌های پایدار دستگاه پرهیز می‌کند، اما حذف پوشه داده یا نصب مجدد ممکن است شناسه را تغییر دهد.
- کلید عمومی داخل برنامه محرمانه نیست؛ کلید خصوصی هرگز نباید در برنامه مشتری قرار گیرد.
- کلید عمومی باید در نسخه انتشار pin شود؛ چرخش کلید نیازمند سازوکار نسخه‌گذاری و پشتیبانی هم‌زمان از کلیدهای معتبر است.

## وضعیت آزمون و باقی‌مانده
تست‌ها امضای معتبر، `key_id` جدید، پذیرش توکن قدیمی بعد از چرخش، رد شناسهٔ کلید ناشناخته، دستکاری توکن، انقضا، محصول/نصب اشتباه، ذخیرهٔ حلقهٔ چندکلیدی، و قرارداد API را بررسی می‌کنند. `dev.ps1 -NoRun` در ۲۰ نوامبر ۲۰۲۶ تست Go، vet و build Qt را گذراند. چرخش واقعی، صدور/فعال‌سازی در محیط staging و production، و تست build روی Windows تمیز هنوز تأیید نشده‌اند.
