# سیاست Migration پایگاه داده

## اجرا

- Migrationها در `internal/adapters/sqlite/migrations/` با نام `NNN_description.sql` نگهداری می‌شوند.
- فایل‌ها در باینری با `embed.FS` قرار می‌گیرند؛ برای اجرای migration به فایل‌های خارجی وابسته نیستیم.
- جدول `schema_migrations` نسخه‌های اعمال‌شده را ثبت می‌کند.
- هر migration در یک تراکنش اجرا می‌شود؛ خطا موجب rollback همان migration می‌شود.
- اجرای مجدد برنامه migrationهای ثبت‌شده را دوباره اجرا نمی‌کند.
- Migration جدید باید شماره افزایشی داشته باشد؛ migration منتشرشده/اعمال‌شده را تغییر ندهید.
- Foreign Key و timeout قفل هنگام بازکردن اتصال تنظیم می‌شوند. برای نسخه فعلی حداکثر یک اتصال هم‌زمان استفاده می‌شود تا PRAGMAهای اتصال قابل پیش‌بینی بمانند.

## نسخه‌های فعلی

1. `001_core.sql`: مشتری، پروفایل صادرکننده، فاکتور و اقلام.
2. `002_payments_indexes.sql`: پرداخت، تخصیص پرداخت، تنظیمات، audit و ایندکس‌ها.
3. `003_invoice_workflow.sql`: metadata محاسبات فاکتور و جدول شمارنده‌های مستقل شماره‌گذاری.
4. `004_templates_letterheads.sql`: سربرگ‌ها، حساب‌های بانکی، قالب‌های سند و ارتباط قالب با حساب‌های منتخب.
5. `005_issuer_profiles.sql`: نوع صادرکننده، نام تفکیک‌شده، شماره‌های تماس و اطلاعات بانکی متعدد.
6. `006_customer_profiles.sql`: نوع مشتری، نام/نام خانوادگی یا نام حقوقی، شماره تماس و نشانی‌های متعدد.

## تغییرات فاز ۴

- اطلاعات موجود با مقدار پیش‌فرض ستون‌های جدید حفظ می‌شوند؛ migration قبلی ویرایش نشده است.
- شماره‌گذاری در همان تراکنش ایجاد پیش‌نویس انجام می‌شود تا شکست درج فاکتور/اقلام شمارنده را rollback کند.

## تغییرات فاز ۵

- Migration چهارم افزایشی است و migrationهای قبلی را تغییر نمی‌دهد.
- قالب و ارتباط حساب‌های منتخب در یک تراکنش ذخیره می‌شوند.

## تست پذیرش

- دیتابیس خالی همه migrationها را تا نسخه ۶ اعمال کند.
- اجرای دوباره migration بدون تغییر schema موفق باشد.
- پروفایل‌های قدیمی و شماره تماس قبلی پس از migration حفظ شوند.
- ذخیره و ویرایش شماره‌های تماس و ردیف‌های بانکی متعدد در یک تراکنش انجام شود.
- Foreign Key فعال باشد و ارجاع نامعتبر رد شود.
- شماره فاکتور تکراری رد شود.
- شکست هر migration، تغییرات همان migration را rollback کند.
- نسخه پشتیبان پیش از ارتقای schema حفظ شود و مسیر بازیابی آزمایش شود.

## محدودیت اعتبارسنجی این تغییر

کد و تست‌ها در مخزن ثبت شده‌اند، اما اجرای `go test ./...` و Build واقعی در این نشست انجام نشده است؛ ابزار Go 1.25.1 و محیط Windows/Qt هدف در دسترس اجرایی نیست. سبز بودن تست‌ها تا اجرای واقعی تأیید نشده است.


## مدیریت مشتری — Migration شماره ۶

- ستون‌های جدید با مقدار پیش‌فرض به جدول موجود اضافه می‌شوند و مشتری‌های قبلی حذف یا بازنویسی نمی‌شوند.
- شماره تماس و نشانی قبلی به جدول‌های فرزند منتقل می‌شوند؛ ستون‌های قدیمی برای سازگاری باقی می‌مانند.
- ذخیره و ویرایش مشخصات مشتری و جایگزینی شماره‌ها/نشانی‌ها در یک تراکنش انجام می‌شود.
- جمع مبلغ فاکتورهای صادرشده و بدهی با واحد پول مستقل (`IRR` و `IRT`) محاسبه می‌شود؛ مبالغ دو واحد با یکدیگر جمع نمی‌شوند.
- تست‌های ذخیره چند شماره/نشانی و تجمیع آمار فاکتورها اضافه شده‌اند؛ تا اجرای واقعی `go test ./...` نتیجه تست تأییدشده نیست.
